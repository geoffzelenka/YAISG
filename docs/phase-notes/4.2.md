# Prompt 4.2 — Estate upgrades and transformation endpoints

Added `GET /estates/me`, upgrade purchase, and form transformation endpoints.
The estate representation resolves the current form content, effective upgrade-slot
cap, installed upgrade names, and active/inert annotations on every request. It also
exposes the relocation fields introduced in 4.1; no relocation behavior was added.

Mutations first run lazy character resolution, then serialize on the home estate
using the existing dialect-aware locking approach. Upgrade purchases validate the
content id, effective free slots, duplicate installation, and item cost before
installing into the lowest free slot. Transformations validate active estate status,
the directed content edge, destination capacity, and item cost before changing only
the form. Both operations charge inventory and commit their estate change atomically,
then emit a structured JSON audit record.

Installed-upgrade applicability is derived rather than persisted, preventing stale
status and modifier/cap caching. Current content can restrict upgrades by realm tags;
the response and derivation path can add form restrictions when a ratified content
field exists, but this prompt does not invent one. No upkeep, decay, solvency,
production, regression, relocation, transfer/escheat, or inter-realm mechanics were
added.

The v1 `WOULD_ORPHAN_UPGRADES` rule rejects a transformation when the destination's
global, form, and realm-node `estate_upgrade_slots` capacity is below the installed
count. Installed-upgrade bonuses are deliberately excluded so an upgrade cannot
justify its own survival. This is the prompt's requested design-ratification note.
Form base caps retain the 4.1 engine convention:
they contribute to the global cap, so the placeholder camp resolves to four slots
(global two plus form two).

Integration coverage includes payload shape and inert reasons, effective XP changes
on subsequent action resolution, all specified error codes, two-session last-slot
contention, cost consumption, camp-to-homestead transformation, destination slot
shrinkage, and a directly simulated busy estate. No content or dependency changes
were needed.
