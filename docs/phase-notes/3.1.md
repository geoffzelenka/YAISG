# Prompt 3.1 — Engine core: lazy resolution loop

Implemented the pure, dataclass-based skilling engine in
`services/game/app/engine/`. The engine resolves full cycles from authoritative
timestamps, preserves partial-cycle time, enforces the offline and inventory
caps, consumes recipe inputs before granting drops, records discarded overflow,
updates XP and levels per cycle, and ends actions with stable stop reasons.

Modifier and cap sources are resolved from the character's realm, active realm
project tiers, and installed upgrades. Upgrade realm-tag mismatches make an
upgrade inert. Percent modifiers sum within their type and are applied once;
drop chance percentages multiply the base chance by `1 + total / 100` and are
clamped to the valid probability range. Integer cycle time and XP results use
truncation after applying the combined percentage.

The standard per-cycle reward calculation implements skilling XP and drop-table
rolls behind a `CycleRewardStrategy` protocol. This keeps the outer timing,
input, inventory, and level loop reusable by the later combat phase without
adding combat behavior now.

The content schema now permits realm project tiers to declare cap bonuses, as
required by design §7.1. No non-goals or game content were added.

The test suite covers exact and partial timestamps, polling associativity,
offline limits, input exhaustion, overflow and input-slot ordering, level-aware
segmented rewards, modifier/inert-upgrade stacking, cap resolution, seeded drop
statistics over 10,000 cycles, recipe conservation with Hypothesis, and action
start validation. Hypothesis was added as a game-service development dependency.

Post-review hardening enforces item stack limits through the same discard log as
distinct-slot overflow, defines inventory overflow as taking precedence over
same-cycle input exhaustion, and leaves an action pending when the offline
budget cannot fit even one cycle. Effective cycle, XP, and drop values are cached
within each level segment and recomputed after a level-up. Empty resolves now
omit zero XP entries. Design §4.2 explicitly records that reaching the offline
cap after progress ends the action, preventing cap-sized repeated polling.
