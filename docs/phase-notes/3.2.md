# Prompt 3.2 — Skilling API and persistence

Implemented the active skilling HTTP surface and its transactional persistence:

- Added Alembic-managed `active_actions` and `reward_log` tables and matching
  SQLAlchemy models, followed by migration `0005` for durable feed claims.
- Added a persistence service that locks the active-action row first, translates
  database state into the pure Phase 3.1 engine, applies deltas, and records only
  productive resolutions. PostgreSQL uses `SELECT ... FOR UPDATE` with a
  character-row fallback when no action exists; SQLite starts an immediate writer
  transaction before loading action state.
- Added available/start/poll/stop endpoints, CSPRNG-seeded per-call randomness,
  and an injectable UTC server clock.
- Added lazy resolution to profile, inventory, and action-availability reads.
- Added durable reward-feed claiming in migration `0005`, so resolutions triggered
  by profile, inventory, availability, or action switches remain visible at the
  next action poll.
- Added integration coverage for start/poll/stop, mid-cycle switching, offline
  catch-up, realm and level gating, timezone-aware responses, reward persistence,
  interleaved reads, and real two-session lock contention.
- Added PostgreSQL 16 to the game-service CI matrix with Psycopg 3 as the test
  driver. CI applies Alembic through head before tests, and the action integration
  fixture uses PostgreSQL so the threaded concurrency test contends on real row
  locks.

One Phase 3.1 bug was fixed: a backwards server-clock correction now produces a
no-op instead of an unhandled `ValueError`. No non-goals or content beyond the
existing placeholder pack were added.

Reward-feed delivery is at-most-once in v1: rows are marked claimed in the same
transaction that prepares the HTTP response, so a disconnected client can miss a
toast without losing character progress. An acknowledged cursor would add
at-least-once delivery if that becomes a product requirement. Reward-log retention
and pagination are likewise deferred until observed data volume justifies a policy.
