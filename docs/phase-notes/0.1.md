# Phase 0.1 — Project skeleton

Built the monorepo skeleton from design §3.1: independent FastAPI auth and game
services, a React/Vite client, empty content and documentation roots, Docker Compose,
and continuous integration.

Both APIs expose only `GET /healthz`, use structured request logging with request
IDs, and have independently configured SQLite databases with WAL enabled. Alembic
has an empty baseline migration for each service. The client displays live health
for both APIs.

Deviations: the supplied path `design/idle-skilling-game-design.md` was absent, so
`design/design.md` was used. CORS middleware was added because the three development
servers use different origins. No game content or game/auth behavior was added. The
host had Docker but neither daemon access nor a Compose plugin, so Compose itself
could not be launched here; its YAML was validated and the same three development
processes were smoke-tested together on their configured ports.

The auth and game services deliberately retain small mirrored infrastructure modules
instead of adding a shared runtime package. This keeps their Docker build contexts and
deployments independent; Phase 0 tests both copies to prevent drift. Alembic metadata
is intentionally `None` until model bases are introduced in later phases.

## Review feedback and actions

The Phase 0 code review found no security-critical problems and identified the
following robustness and maintainability improvements.

1. **Request logging on exceptions — fixed.** The middleware now assigns the generated
   request ID to `request.state` before invoking a handler. Unhandled handler exceptions
   produce the standard public 500 response with the same `X-Request-Id`, and the request
   is logged as structured JSON with method, path, status, duration, request ID, and
   exception type. Each service has a regression test that raises a handler exception
   and verifies that the response and log contain the same request ID. The middleware
   returns the controlled 500 response instead of re-raising because an outer framework
   error response could not reliably retain a header added by the request middleware.

2. **Build version injection — fixed.** Both Dockerfiles accept a `GIT_SHA` build
   argument and expose it to the service environment. Compose accepts `GIT_SHA` from the
   host and defaults to `dev`; GitHub Actions supplies the checked-out commit SHA.

3. **Duplicated service infrastructure — retained deliberately.** A shared runtime
   package was considered but not introduced. The auth and game services are intended
   to remain independently buildable and deployable, and sharing code would require a
   broader Docker build context and cross-service packaging for a small amount of Phase
   0 infrastructure. The mirrored modules and settings remain synchronized and are
   covered by the same checks and equivalent tests. This tradeoff should be revisited if
   the duplicated infrastructure grows.

4. **Docker build context size — fixed.** Service `.dockerignore` files exclude caches,
   virtual environments, test artifacts, and local data. The client `.dockerignore`
   excludes `node_modules`, build output, and coverage output, preventing host-generated
   dependencies from replacing the container's `npm ci` installation.

5. **CORS configuration — fixed.** Allowed origins now come from the `CORS_ORIGINS`
   environment variable, defaulting to `http://localhost:5173`. All HTTP methods are
   permitted at the middleware level so Phase 1 POST requests will pass preflight;
   application routes still determine which methods actually exist.

6. **Alembic metadata — documented.** Both Alembic environments explicitly set
   `target_metadata = None` because Phase 0 contains no models. Inline guidance records
   that this must be replaced with the appropriate `Base.metadata` when models arrive.

7. **CI and Makefile duplication — fixed.** GitHub Actions installs each job's
   dependencies and delegates checks to `make auth-ci`, `make game-ci`, or
   `make client-ci`. The Makefile is now the single definition of the commands run both
   locally and in CI.

8. **Duplicate CI runs — fixed.** Push-triggered CI is limited to `main`, while pull
   requests continue to run normally. A concurrency group cancels superseded runs for
   the same workflow and Git ref.

9. **SQLite thread use — fixed.** SQLite engines now set
   `check_same_thread=False`, preparing them for FastAPI synchronous thread-pool access
   when database sessions are added. Other SQLAlchemy dialects do not receive this
   SQLite-specific connection argument.

10. **Health status colors — fixed.** The client uses neutral gray while a health check
    is loading, green when healthy, and amber when unavailable. The client test verifies
    the loading and healthy states.

## Verification

After the review changes, `make ci` passed in full:

- Ruff lint and formatting checks passed for both Python services.
- Strict mypy checks passed for both Python services.
- Both services passed their health and exception-path tests (four Python tests total).
- ESLint, Prettier, and TypeScript checks passed for the client.
- The client Vitest test and Vite production build passed.
- Both empty Alembic baselines upgraded successfully and SQLite WAL mode was verified.
- The GitHub Actions workflow and Compose file parsed as valid YAML with the expected
  jobs and services.

The development processes were also smoke-tested together: both health endpoints
returned successful envelopes with `X-Request-Id` headers, and the Vite page was served.
As noted above, this environment did not provide Docker daemon access or a Compose v2
plugin, so the exact `docker compose up` command could not be executed here.
